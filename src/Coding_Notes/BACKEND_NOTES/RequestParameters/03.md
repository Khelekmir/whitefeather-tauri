Here’s a breakdown of which of your endpoints would be *more semantically correct* (and flexible) if switched to use **query parameters**, and which ones are fine as **path variables**:

---

### ✅ Should be **Query Parameters** (these are filters):

```java
@GetMapping("/byType")
public ResponseEntity<List<EquipmentItem>> getAllByType(@RequestParam String itemType)

@GetMapping("/byName")
public ResponseEntity<List<EquipmentItem>> getAllByName(@RequestParam String itemName)

@GetMapping("/byCharacter")
public ResponseEntity<List<EquipmentItem>> getAllByCharacterName(@RequestParam String characterName)

@GetMapping("/bySlot")
public ResponseEntity<List<EquipmentItem>> getAllBySlot(@RequestParam String itemSlot)
```

### Why?

These endpoints filter the equipment **collection** by some attribute. In RESTful terms, that’s best represented by query parameters:

```
GET /api/equipment?type=sword
GET /api/equipment?name=Iron+Shield
GET /api/equipment?characterName=Lyn
GET /api/equipment?slot=offhand
```

These could even be combined later:

```
GET /api/equipment?characterName=Lyn&type=sword&slot=mainhand
```

---

### ✅ Keep as **Path Variable**:

```java
@GetMapping("/{id}")
public ResponseEntity<EquipmentItem> getEquipmentItemById(@PathVariable int id)
```

### Why?

This is retrieving a **specific resource by ID**, which is canonical REST:

```
GET /api/equipment/42
```

---

### 🧠 Summary Rule of Thumb:

| Use Type        | When to Use                                                      |
| --------------- | ---------------------------------------------------------------- |
| `@PathVariable` | Accessing a single, specific resource (e.g., by `id`)            |
| `@RequestParam` | Filtering/searching a collection (e.g., by `type`, `name`, etc.) |
